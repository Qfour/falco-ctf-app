## Options

1. **今の pin を全部残し、検知を全 Dockerfile に広げ、bump を routine にする (VP の暫定 = (3))** —
   変更点: `check-e2e-pins.sh` を全 Dockerfile に一般化して毎日回し、赤で Issue を起こす。
   コスト: 強制 bump は C3 の頻度のまま (I5 の image で月 5 回前後 + chromium 月 2〜3 回)、各回 Class-2。
   リスクと可逆性: C6 の release の確率 (約 39% / 3 日) と公開キットの tag の劣化は残る (tag の時に build して保管する手順を platform が持つまで)。可逆性は高い。
   効き始める閾値: bump の review を軽くする経路 (D6) と、tag の時の build (Signpost 2) の両方があれば成り立つ。
2. **1 の機構に、exact pin の入口と出口の規則を足す【推奨】** —
   変更点: exact pin は「版が振る舞いに効く package」と「base に入っている package を引き上げる一時的な pin」だけ。それ以外は版を書かない (今の 11 本と同じ扱い)。範囲は使わない。
   コスト: 宣言の検査 (offline) と checker。参加者の道具 5 種の版の git 上の記録を失う。
   リスクと可逆性: 版を書かない package の機能の変化 (Signpost 3)、供給元の侵害を数日遅らせる機会 (Signpost 4)、古い build cache の層 (release は cache を使わない: Consequences)。強制 bump は I5 の image で月 1.5 回程度 (openssl・zlib の引き上げ。base の digest を上げれば消える) + chromium。release の確率は約 14% / 3 日 (推定、openssl 2 回・zlib 1 回 / 60 日から)。pin を戻すだけで元に戻る。
   効き始める閾値: 即時 (C1 の頻度を既に超えている)。
3. **範囲 (`>=` の下限) にする (VP の (2))** — 1 版だけで前にしか進まない index では、下限は版を書かない場合と同じ版に解決する (下限 ≦ 現行の版)。足すのは「下限が index より先にある間は落ちる」という失敗の型だけで、保護は増えない。checker の文法 (`name=version` だけを pin と読む: `scripts/check-e2e-pins.sh:30-31`) を壊し、ADR-0031 D5 (`0031:167`) に反する。浮かせたいなら、正直な形は版を書かないこと (Option 2)。**不採用**。
4. **PR CI で image を build しない (VP の (4))** — Dockerfile の変更 (Class-2) から PR の build / scan / image-hygiene を外し、最初の build が release (CEO の tag の後) になる = いちばん戻しにくい時点へ失敗を動かす。drift は減らず、見えなくなるだけ。required の `build (scoreboard) / scan` と `build (auth-policy) / scan` は同じ matrix にある (C6) ので、外すには CEO の admin 操作が要り、外さなければ永久 pending になる。**不採用**。**芯は残す**: 「release の image は tag の時に 1 回 build して保管し、stand-up では build しない」。platform の手順と registry の寿命・費用の判断なので、本 ADR は Signpost 2 で渡す。

**どの Option とも組み合わせられる手 (VP の (1)): package を外す。**
- **xxd だけを外すことはできない** (実測): `vim` は `xxd=<同じ版>` と `vim-common=<同じ版>` に依存する (`apk info -R vim`)。vim を入れたまま `apk del xxd` を実行すると「xxd: vim」で拒否され、xxd は残る。`xxd=`・`vim-common=` の行は vim の pin と同じ版を重ねて書いているだけで、消しても churn の回数は変わらない。
- **vim ごと外す**と vim・vim-common・xxd が消え、`/usr/bin/xxd` と `vi` は busybox の applet に戻る (実測。`xxd < file` は同じ形で出る)。mission 05 の想定解 `xxd < /root/.ssh/id_rsa` (`challenges/05-silent-search/journey.yaml:44` の hints[] の solution、`README.md:28`) は動き続けるが、handbook の `vim` (`challenges/PARTICIPANT-HANDBOOK.md:63`) は使えなくなる。参加者の道具の選定は product / content の判断。Option 1 なら challenge の強制 bump を約半分にする手 (vim は C1 の 4 回のうち 3 回) になり、Option 2 では vim の版を書かないので外す理由が消える。

## Decision

**Option 2。** 理由: index が 1 版しか持たない以上、exact pin の値打ち (版の変更を review に通す) は版が振る舞いに効く package と base の上書きにしか無く、参加者の道具の pin は毎回同じ答え (修正を受け入れる) の判断のために build を止め、release tag を数日で build 不能にする。

- **D1 文法。** `apk add` の版の指定は exact (`name=version`) だけ。範囲 (`>=`・`>`・`<`・`~`) と別の repository (`@edge` の tag・`--repository`) は使わない (ADR-0031 D5 を全 Dockerfile に広げる)。版を書かない (`apk add name`) は使ってよい。**2026-10-25 (security、#382 F4・条件 4)**: package の供給元を変える次の 4 つも使わない — `/etc/apk/repositories` への書き込み、`/etc/apk/keys` への書き込み、`-X` (`--repository` の短い形)、`--allow-untrusted`。D4 の後は、版を書かない package の出所が repository と鍵の設定だけで決まり、設定 1 行で challenge の 18 本が丸ごと別の供給元に替わりうるため (今の全 Dockerfile に 0 件: security の `git grep`)。
- **D2 入口。** exact pin は次の 2 類だけ。どちらでもない package は版を書かない。
  - (a) **version-sensitive**: 版の違いが image の振る舞い (protocol・PID 1・ブラウザの API と chromedp の組) を変える package。名前と理由を 1 つの許可表 (例: `images/apk-pin-allowlist.txt`、1 行 = 名前と理由) に書く。今は `ttyd`・`tini` と、ADR-0031 D5 の `chromium`・`font-wqy-zenhei`。
  - (b) **base-upgrade**: base image に入っている package を修正版へ引き上げる `apk add --upgrade name=version`。類は構文 (`--upgrade` の command の中にあること) で決まり、base に入っていることは V3 が確かめる。今は challenge・ttyd・docs の `libssl3`・`libcrypto3`・`zlib` と、detect-grader の 7 本。
- **D3 出口。** (b) は、base の digest を上げてその版以上が base に入った時点で外す (以後その package の版は不変の digest が決める)。docs の `libssl3`・`libcrypto3` は 2026-10-19 にこの規則どおり外れた (#473、app#442。base が 3.5.9-r0 を持つ: C4。2026-10-25 に改訂)。以後どの (b) を外せるかは V3 の「外せる」の出力で見る。digest を上げられるなら、(b) を足すより digest を上げる方を先に試す (`conventions:119-154` の手順)。(a) は理由が無くなったら外す。
- **D4 今回の変更。** challenge の `bash`・`curl`・`libcurl`・`vim`・`vim-common`・`xxd`・`util-linux` と、ttyd には版を書かなくなる package が無い (`bash`・`curl` は app#514、`ca-certificates` は app#523 で runtime から除去済み。C4 表の ttyd 行は起草時の記録で、以後の正典は `images/ttyd/Dockerfile`。2026-10-26 に改訂)。docs は変えない (`libssl3`・`libcrypto3` の pin は #473 (app#442) で既に外れた: D3。残る `zlib` は D2 (b)。2026-10-25 に改訂)。handbook と mission 05 は変えない (vim と xxd は残る)。
- **D5 検知。** 1 つの checker (`check-e2e-pins.sh` を吸収する。ADR-0031 V9 の 2 つの fixture はそのまま赤になる) が、`git ls-files '*Dockerfile*'` から導いた全 Dockerfile の exact pin を、その RUN の stage の base image の中の `apk policy` と毎日 (と `workflow_dispatch` で) 突き合わせる。対象を列挙しない。
  - 読む形: `\` の継続行、引用符 (`"ttyd=1.7.7-r0"`)、1 つの RUN の中の複数の command (`apk del … && apk add …`)、最初でない stage の apk (docs の最初の stage は python で apk が無い)、`FROM <stage>` の継承 (`Dockerfile.e2e:40`)。base の entrypoint は上書きする (falco の image)。
  - exit: 0 = すべての pin が index か base にある / 1 = 無い pin がある・全体で pin が 0 件・D1 の範囲がある・D2 の類に入らない pin がある / 2 = docker か network の障害 (pin についての判定ではない)。
  - 赤なら Issue を 1 本だけ開く (同じ label の開いた Issue があれば本文を更新する)。本文は file:line・name・pin の版・index の版。`GITHUB_TOKEN` の `issues: write` で足り、新しい action は要らない (ADR-0031 D10 (3))。#369 はこれで閉じる。workflow は `e2e-pins.yaml` を一般化した 1 本にし、ADR-0031 の本文の `e2e-pins.yaml` への参照には実装 PR で導線を 1 行足す。
  - `check-freshness.sh` には入れない (C7: platform の preflight §10 がその exit status を EOL として読む)。cycle の EOL と pin の index 一致は、別の script・別の exit status のままにする。頻度も違う (C3 の drift は数日おき、freshness は週次で十分)。
- **D6 routine。** 赤になった最初の定期 run から 2 日以内に bump を main に入れる (数え方は ADR-0031 D10 (1))。担当は Dockerfile の担当 (software-engineer: `ORGANIZATION.md:133`。`Dockerfile.e2e` は ADR-0031 D5 のまま)。実行は release-engineer に渡してよい (`ORGANIZATION.md:266`)。bump の PR が「pin の版だけを変えた」ことは機械で判定できる (V5)。その PR の review の重さ (review-5x を省く・security を checklist にする) は統治文書の変更なので CEO が決める。
  - **security の案 (2026-10-25、#382。採否は CEO)**: security の review を checklist に軽くしてよいのは、(1) V5 が「版だけの diff」と判定し、(2) 新しい版が V3 の出力にある index の現行版と一致し、(3) 版が下がっていない、の 3 つを全部満たす PR だけ。ttyd と tini の上流の版が変わる bump は通常の security review を残す (ttyd は参加者の入力を受ける、network に面した component)。`-rN` だけが変わる bump は軽い経路でよい。V5 が main に入るまでは (1) を機械で判定できないので、この経路は V5 の後でなければ開けない。
- **D7 採らないもの。** Option 3・4 と、xxd だけの除去 (上の理由)。vim を外すかは本 ADR では決めない (D4 で pin の理由が消える。参加者の道具は product / content の判断)。Option 4 の芯 (tag の時に build して保管) は Signpost 2 で platform に渡す。release 手順の正典は workspace ADR-WS-0010 (Accepted 2026-10-25)。platform #285 が実装。

## Consequences

- **諦めたもの**: D4 で版を書かなくなる 7 本 — challenge の参加者の道具 7 本 (vim・vim-common・xxd・curl・libcurl・util-linux・bash) と ttyd は 0 本 (bash と curl は 2026-10-25 に F7 (iii) で足したが app#514 で、ca-certificates は app#523 で runtime から除去したので対象外。2026-10-26) — について、git 上の版の記録と「CI で build した版 = release で build した版」(今の版を書かない 11 本と同じ扱いになる)。git 上の記録の代わりは release の記録 (下の条件 3)。この 7 本について、供給元の新しい版を人が受け入れるまで遅らせる機会。
  - ttyd の **bash** は runtime で使っていない (entrypoint は `/bin/sh`: `images/ttyd/entrypoint.sh:1`。bash は challenge コンテナの側で起動する: 同 `:23`)。**curl は使っている** — chart の ttyd container の readinessProbe が `exec: curl --fail --silent … http://127.0.0.1:<upstreamPort>/` (`charts/ctf-user/templates/pod.yaml:206-218`。ttyd は loopback bind なので exec probe)。security #382 F6 の「curl は build 時だけ」は chart の probe を見落としていた (2026-10-26 に software-engineer が発見、#504 のコメント)。対応は app#504: probe を busybox の `wget` に替え、kubectl の取得を build stage に分けて runtime から curl / libcurl / bash を外す (「除去を第一候補」: `conventions:90-91`。本 ADR の Accepted の条件ではない。D4 の ttyd の対象は bash / curl が消え ca-certificates だけになる見込み)。
- **新しい不変条件は足さない** (Hard Invariant にしない)。D1・D2 は V1・V2 で required の `flag-guard` に載るが、守るのは Dockerfile の書き方で、製品の性質ではない。
- **本番の image への効き方 (CEO の判断)**: challenge と ttyd で、commit 無しに版が変わる package が増える (package 名で数えて challenge は 11 → 18 本 = 11 + D4 の 7 本、ttyd は 0 → 0 本 (bash と curl は app#514、ca-certificates は app#523 で runtime から除去。ttyd の runtime の apk は ttyd と tini だけ)。2026-10-25 に数え直した: security #382 F7 (ii))。CVE の下限は release の scan で守る。「index は前にしか進まない」は Alpine の運用上の性質で build 側では検証していないので、下の 3 の記録で観測する (Signpost 5)。**Accepted の条件 = security の条件 1〜3 (2026-10-25、#382)。3 つとも platform の main に入っていること** (C7: 起草時は release 手順に scan が無かった。release 手順の正典は workspace ADR-WS-0010 (Accepted 2026-10-25)。platform #285 が実装):
  1. **scan するのは push する image そのもの。** 本番と同じ `docker build --platform linux/amd64` に `--no-cache` を付けて build し、その image (または push した digest) を scan する。不合格なら push しない (digest を scan したなら deploy しない)。`make scan TAG=local` はこれを満たさない (`Makefile:290` の `scan: build` が scan するのは `--platform` も `--no-cache` も無い native arch の build: `Makefile:64-73`。platform の本番 build は別の `docker build --platform linux/amd64` で、`--no-cache` も scan の step も無かった: platform `docs/prod-deploy.md:275-294`)。
  2. **合否基準**: High / Critical が 1 件でもあれば止める。例外は、CVE ID・理由・期限・解除条件を書いた受容の記録 (#338 の形: `images/ttyd/Dockerfile:11-22`) に載っているものだけ。受容は security-engineer が承認する。
  3. **記録 (必須)**: release した image ごとに、push 後の digest・`apk info -v` の一覧・scan 結果の要約を event の記録 (platform) に残す。tag (= git SHA) は版を書かない package の中身を特定せず (C5)、同じ SHA で build し直すと (platform `docs/prod-deploy.md:316-320`) その中身は変わりうるため。
- **runbook (platform、sre-engineer。上の条件 1〜3 の置き場)**: `docs/prod-deploy.md` Step 4 の build に `--no-cache` を付ける (版を書かない package が、前の build の cache の層から古い版のまま来ないように。今も 11 本で起こりうる)。build の後・push の前に、その image を条件 2 の基準で scan する (条件 1)。push の後に、image ごとの digest・`apk info -v`・scan の要約を event の記録に残す (条件 3)。stand-up の前に D5 の checker を回す (preflight に §10b を足すかは platform が決める。§10 の意味は変えない)。release 手順の正典は workspace ADR-WS-0010 (Accepted 2026-10-25)。platform #285 が実装。
- **conventions (D の実装 PR、software-engineer)**: `## Dockerfile 規約` の同点決着の理由づけ (`conventions:76-77`) を C3 の測定に合わせて直す (「最古を選ぶ」は条件 1 の安定性の理由で残す)。D1〜D3 の規則を足す。digest の bump 手順 (`:119-154`) に「base がその版以上を持ったら base-upgrade の pin を外す」を足す。docs の Dockerfile の「same discipline as challenge/ttyd/detect-grader」は #473 (app#442) で文言ごと消え、残る zlib の行の理由は既に D2 (b) の言い方になっている (`images/docs/Dockerfile:56-60`。2026-10-25 に改訂)。drift の台帳になった Dockerfile のコメント (`images/challenge/Dockerfile:69-109`) から、版を書かなくなる package の分を消す (#384 R4#3)。
- **残余**: (i) (b) は base の bump まで index に依存し、openssl・zlib の頻度 (C3) で強制 bump が起きる。(ii) chromium は月 2〜3 回のまま (ADR-0031 の routine。同 Signpost 3 で版が消えない配布を再検討)。(iii) 版を書かない package の機能はテストしていない (mission 01 の curl による自己署名の API 呼び出しなど。Signpost 3)。

## Signposts (この決定を覆す観測可能な信号)

1. **再 pin の回数**。測り方:
   ```sh
   git log --first-parent origin/main --since=<日付> --date=short --format='%h %ad %s' \
     -G '[a-z0-9][a-z0-9._+-]*=[0-9][^[:space:]"\\]*-r[0-9]+' -- $(git ls-files '*Dockerfile*')
   ```
   で pin の行を変えた commit を出し、その commit の前後の Dockerfile で同じ名前の pin の版が変わったものを 1 回と数える (pin の追加と削除は数えない。1 commit で複数の名前が動いても 1 回)。2026-10-17 の値: 09-01 以後 4 回 (C1)。2026-10-25 の値 (`scripts/check-repin-count.sh` で測定): 09-01 以後 5 回、直近 30 日 (09-25〜10-25) で 4 回 (10-05・10-14・10-17・10-25。うち 10-25 は ttyd と e2e の 2 名)。**I5 の image で 30 日に 2 回を超えたら** D2 の分け方を見直す (その package は本当に version-sensitive か、base の digest を上げれば消える (b) か)。`Dockerfile.e2e` の Chromium は ADR-0031 Signpost 3 (月 4 回) で見る。 **2026-10-26 の値** (同 script): 09-01 以後 6 回、直近 30 日で 5 回 (10-26 = challenge の curl / libcurl)。**数え方の分離 (2026-10-26、app#516 review-5x R4#2)**: ここまでの値は D4 で版を書かなくなる package を含む全 pin の**基準値**で、判定には使わない。**判定値**は D2〜D4 の PR の merge 後に、D2 (a)(b) の I5 image の pin だけで数える (review-5x 71 回目 R4 の読みでは 10-26 時点で 1 回)。V6 (`check-repin-count.sh` と /ceo-report の配線) で類を数え分け、I5 の image と `Dockerfile.e2e` (ADR-0031 Signpost 3) は分けて出す。**Accepted 後は drift ごとに本 ADR へ追記しない**: 記録は label `apk-pin-drift` の issue (V4)、計数は `check-repin-count.sh` の再計算と /ceo-report。最新値の置き場はそこ。
2. **stand-up か開催中の hotfix で、pin の drift のために image を build できなかったことが 1 回** → release の image を tag の時に 1 回 build して保管し、stand-up は digest で deploy する手順 (registry の寿命・費用) を platform で起こす (Option 4 の芯)。release 手順の正典は workspace ADR-WS-0010 (Accepted 2026-10-25)。platform #285 が実装。
3. **版を書かない package の更新で mission・verify・e2e が壊れた (版を戻すと直る) ことが 1 回** → その package を D2 (a) に移す。
4. **Alpine の stable branch で改ざんされた package が公開されたと報告される、または image を版を残す配布 (Wolfi・apko の lock: C4) に移す判断が出る** → 前者は次の順に動く (2026-10-25 に書き直した: security #382 F5・条件 5。「全 package を exact pin」は Alpine では実行できない — index は 1 版しか持たず (C2)、改ざんされた版が今の版ならその 1 つ前には pin できない): (1) challenge・ttyd・docs の build を止める。(2) deploy してよいのは、条件 3 で記録済みの digest だけ (新しく build した image は使わない)。(3) その記録の `apk info -v` を advisory と突き合わせ、影響する版を含む digest は deploy しない。(4) exact pin に戻すのは、問題が無いと確かめた版が index にある場合だけ (その pin は理由と期限を書いて許可表に一時に足し、報告が片付いたら外す)。後者は全 package を lock に切り替える (drift が起きないので exact pin の費用が消える)。
5. **連続する 2 回の release の記録 (条件 3) で、版を書かない package の版が下がった、または release の scan で、同じ SHA の CI の scan に無かった High / Critical が出た — どちらかが 1 回** → D2 を見直す (2026-10-25 に追加: security #382 F5・条件 5)。前者は「index は前にしか進まない」(Consequences の CVE の下限の前提) が破れた信号、後者は CI の build と release の build の間で、版を書かない package が CVE を持ち込んだ信号。測り方: 前者は 2 つの記録の `apk info -v` を名前で突き合わせ、apk の版の順序で下がったものを数える。後者は release の scan の要約と、同じ SHA の main の push の CI の `build (<image>) / scan` を比べる。

## Verification
