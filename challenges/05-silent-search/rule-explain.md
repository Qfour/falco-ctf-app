### ルールの読み方

これは **回避 (evade) ミッション**。Mission 04 で発火させた
`Search Private Keys or Passwords` を、今度は**鳴らさずに**目的を果たす。
まず、このルールが「何を根拠に」判定しているかを押さえる。

| condition の断片 | 意味 |
|---|---|
| `spawned_process` | プロセスが新規に `exec` された瞬間を対象にする |
| `grep_commands and private_key_or_password` | `grep` 系で、かつ引数に鍵/パスワードのパターンを含む |
| `proc.name = "find" and proc.args contains "id_rsa"` (等) | `find` で、引数に鍵ファイル名を含む |

Mission 04 と同じく、判定材料は **`proc.args` / `proc.cmdline` = exec 時の
コマンドライン文字列**だ。`output` の `command=%proc.cmdline` にも、その起動時の
引数がそのまま残る。ルールは**「特徴語を含むコマンドラインで起動されたこと」**を
見ており、その後にプロセスが何を読んだかまでは追っていない。

### なぜ発火しない (リスクが低い) のか

ファイルの中身を得る方法は「ファイル名を引数に渡す」だけではない。**引数に機微な
ファイル名を一切載せずに**同じ中身へ到達する経路がシェルには複数ある (入力の
受け渡しの仕方を変える等)。すると exec されたプロセスの `proc.cmdline` には
特徴語 (`id_rsa` 等) が現れず、`proc.args contains "id_rsa"` が偽になって発火しない。

これも「検知を破壊した」のではなく「**コマンドラインシグネチャの死角に入った**」
だけだ。リスクが低いと言えるのは、(1) 攻撃者に引数を隠すという追加の工夫を要求でき、
(2) 実際のファイル読み出しは下記の別ルールで捕捉余地が残るから。**コマンドライン
文字列だけに依存した検知は回避されやすい**、という点がこのミッションの学びだ。

### Sysdig のマネージドルールでのカバー

コマンドライン隠蔽で抜けても、**「実際に機微ファイルを読んだ」という行為**は別の
ルールで捕まえられる。Sysdig のマネージドルールセットはこのシナリオを面で押さえる。

- **ファイル読み出しベースの検知** — `Read sensitive file untrusted` のように、
  コマンドラインではなく **open された対象**を見るルールが、鍵ファイルの読み出し
  そのものを捕捉する (cmdline を隠しても読み出しは残る)。
- **相関** — Sysdig Secure は「鍵探索の試み」「鍵ファイルの読み出し」「外部への
  送信」を同一プロセスツリー上で関連付け、コマンドライン検知が 1 つ抜けても
  シナリオ全体としてアラートを積み上げる。

つまり、**cmdline 一本で書いた自作ルールは引数隠しで抜けられるが、Sysdig の
マネージドポリシーは読み出しイベント + 相関でこのシナリオをカバーする**。
