### ルールの読み方

これは **回避 (evade) ミッション**。発火させてはいけないルール
`Read sensitive file untrusted` が、何を見て何を見ていないかを理解すると、
すり抜けの原理が見えてくる。

| condition の断片 | 意味 |
|---|---|
| `open_read` | ファイルを**読み取り目的で開く** (`open`/`openat`) イベント |
| `sensitive_files` | 開いた **path** が機微ファイルのパターン (`/etc/shadow`, `/etc/sudoers` 等) に一致 |
| `proc_name_exists` | プロセス名が取れている (異常イベントの除外) |
| `not proc.name in (...)` | `sshd` / パッケージ管理 / シェル等、**正当に機微ファイルを触るバイナリ**を大量に除外 |
| `not ... (多数の例外)` | Ansible・Chef・cron 等、運用ツールによる正常アクセスを除外 |

判定の要は `sensitive_files` が **`fd.name` (open に渡した path 文字列)** で
マッチする点だ。`output` の `file=%fd.name` を見ればわかるとおり、Falco が
記録するのは**解決後の実体パスではなく、呼び出し側が渡したパス文字列**。

### なぜ発火しない (リスクが低い) のか

同じファイル本体 (inode) には、`/etc/shadow` 以外の path 経由でも到達できる。
Linux にはプロセス視点の代替パス (プロセスの mount namespace ルートを指す
`/proc/<pid>/root/...` など) が存在し、そこを通すと `fd.name` が
`/etc/shadow` パターンにマッチしなくなる — だから**このルール**は鳴らない。

ただし、これは「検知を消した」のではなく「**このルールの視野の外に出た**」だけだ。
リスクが相対的に低いと言えるのは、(1) 攻撃者側に「path 判定を回避する」という
一手間と知識を強制でき、(2) 別レイヤ (下記) で捕捉の機会が残るから。path 一本に
依存した検知は脆く、多層で見るべき、という教訓がこのミッションの核心だ。

### Sysdig のマネージドルールでのカバー

path 文字列だけに頼るこの回避は、**フィールドを変えたルール**で塞げる。Sysdig の
マネージドルールセットは同じ機微ファイル読み出しを複数の角度から監視しており、
シナリオ全体としては次の層でカバーされる。

- **代替パス読み出しの明示検知** — `/proc/*/root/...` のようなプロキシパス経由の
  機微ファイルアクセスを狙って捕捉するルールが用意されている。
- **inode / 実体ベースの判定** — path 文字列ではなく開かれた対象の実体で評価する
  設計に寄せることで、別名でのアクセスを吸収する。
- **相関** — Sysdig Secure は単発イベントを Pod / Namespace / プロセスツリーと
  紐付けるため、「機微ファイルへの回避的アクセス」というパターンとして浮かび上がる。

要するに、**自作の単一ルールを path で書くと抜けられるが、Sysdig のマネージド
ポリシーはこのシナリオを別フィールド・別ルールで面として押さえている**。
