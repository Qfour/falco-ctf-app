# Falco のしくみ

Falco が「何を」「どう見て」アラートを出すのかを、順番に追ってみます。
これが分かると、各ミッションの検知ルールが何を検査しているのかを
自分で読み解けるようになります。

## 1. syscall キャプチャ — Falco はまず「何が起きたか」を集める

Falco はホスト / コンテナで実行されるあらゆるプロセスの **syscall
(システムコール)** をカーネルレベルで観測します。ファイルを開く・
プロセスを起動する・ネットワーク接続を張る・パーミッションを変える
… といった OS への要求はすべて syscall を経由するため、Falco はここに
フックすることで「ユーザ空間のプログラムが何をしたか」を横取りできます。

ポイントは、**アプリケーションのログではなく OS の一段下を見ている**
ということです。プログラムが自分の行動をログに残さなくても、
コマンドを工夫してログ出力を消しても、syscall そのものは必ず発生する
ので観測から逃れられません。

## 2. イベント化 — 生の syscall が構造化されたフィールドになる

観測した syscall は、単なる 0/1 の羅列ではなく **構造化されたイベント**
に変換されます。「どの syscall だったか」「誰が (どのプロセスが) 呼んだか」
「どのファイル / どの宛先に対してか」といった情報がフィールドとして
取り出せる形になります。この「フィールド化されたイベント」が、次の
rule 評価の入力になります。

## 3. rule 評価 — condition という論理式にイベントを当てる

Falco には多数の **rule** が定義されています。各 rule は
`condition` という論理式 (`and` / `or` / `not` で組んだブール式) を持ち、
1 つのイベントが流れてくるたびに、ロードされている全 rule の
condition に当てはめて **真になるかどうか** を判定します。真になった
rule だけがアラートを生成します。

「rule condition の読み方」の章で、この condition 自体をどう分解して
読むかを扱います。

## 4. output と priority — アラートに意味と重みをつける

condition が真になると、その rule に定義された `output` テンプレートが
実際のイベント値で埋められ、1 行の説明文になります。同時に `priority`
(`emergency` 〜 `debug` のような重大度ラベル) が付きます。この
output + priority が、実際にダッシュボードやログに流れる「検知結果」
の実体です。

## 5. 全体の流れ

```
syscall (kernel)
   ↓ キャプチャ
構造化イベント (evt.type / proc.* / fd.* などのフィールド)
   ↓ 全 rule の condition と照合
条件が真になった rule
   ↓
output (証拠の説明文) + priority (重大度)
```

この一連の流れを頭に入れておくと、「なぜこの操作で検知されたのか」
「なぜこの操作では検知されなかったのか」を、結果を見るだけでなく
**過程から** 説明できるようになります。次の章では、rule の
`condition` そのものをどう読み解くかを見ていきます。
